Evaluation Rubric

This repo is built to satisfy a specific, explicit rubric — the same one a staff/lead engineer or hiring panel actually uses when screening a candidate's code, not just "does it work." Naming it here, rather than leaving it implicit, is itself part of the point: it should read as "thinks like the reviewer," not "produced a portfolio for the reviewer."

Failure-mode judgment (does this person anticipate the way production breaks and fix it correctly) is one axis of nine. All nine are demonstrated across the 4 pipelines below, not asserted in prose.

# What's screened for Where it's demonstrated
1 Correctness & failure-mode judgment — anticipates how production actually breaks All 8 issues in pipelines/*/BUILD_LOG.md
2 System design / scope judgment — right-sized for the problem, no premature complexity, a stated path to scale Each pipeline's README "Architecture, in 5 lines"; crypto/pipeline.py's chunking note explicitly scopes what's claimed vs. not
3 Testing discipline — tests that would actually catch a regression, not coverage theater Every tests/ suite: xfail-proves the bug against before/, then proves the fix — see "How the tests are structured" below
4 Observability — can you tell what happened after the fact from logs alone pipelines/*/observability.py — structured (JSON) event emission, not free-text prints
5 Security & data-handling — secrets management, least-privilege, input validation as a security boundary No secrets anywhere in this repo (every live source is a public, keyless API); ecommerce/pipeline.py's validate_record() treats untrusted input as a boundary, not just a correctness nicety
6 Numerical/data correctness — the subtle-bug class that's easy to ship and expensive to miss finance/pipeline.py issue #2 (GBX/GBP/USD unit confusion) — a real, well-known finance gotcha, not a contrived one
7 Tradeoff reasoning — states why this design, not a heavier one, out loud crypto/BUILD_LOG.md's "Note on framing" section; finance/pipeline.py's module docstring on I/O-vs-logic separation
8 Documentation & communication — a reviewer understands the "why" fast Every BUILD_LOG.md (Issue / Impact / Root Cause / Fix / Prevention); no filler comments anywhere, only ones that carry a non-obvious reason
9 Incident-response / postmortem discipline — diagnose, document, fix, prevent The BUILD_LOG.md format itself, applied consistently across all 4 pipelines

How the tests are structured

Every pattern in this repo is proven twice, not once:

  1. A test marked @pytest.mark.xfail(strict=True) runs against the before/ implementation — the naive, pre-fix version, kept in the repo rather than deleted. It fails for the specific documented reason. If this test ever unexpectedly passes, strict=True fails the suite — the naive code stopped being naive, and the log is now wrong.
  2. A normal passing test runs against the real, current pipeline.py — the fix.

This means pytest output alone — no prose, no trust required — shows both "this bug is real" and "this fix resolves it." Run it: pytest -v from the repo root.

What this repo is / isn't

Is: four small, real, runnable pipelines (Finance, Crypto, Ecommerce, Solar) — the same four verticals this account has already shipped live, public capability demos for — each built to make two specific, realistic production failure modes concrete, tested, and documented like a real incident review.

Isn't: a framework, a claim that any specific employer's actual architecture looks like this, investment/trading advice, or a certification claim of any kind. Every "what this is / isn't" note inside each pipeline's own README is the authoritative scope statement for that pipeline.
