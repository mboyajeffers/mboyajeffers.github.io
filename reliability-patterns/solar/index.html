Solar Pipeline

What it does: ingests per-site irradiance data with staleness monitoring, and runs a resumable multi-step per-site computation (live source: Open-Meteo's free forecast API, no key — the same real source used elsewhere in this account's public solar capability demo).

Architecture, in 5 lines: fetch_live_irradiance() hits the network per site → HealthMonitor.record_success() timestamps every success so stale_sites() can flag a site that's gone quiet → separately, PipelineRun carries a persisted state through fetch → normalize → compute → write, and advance_one_step()/run_to_completion() always resume from the last completed step instead of the top.

What this proves — see BUILD_LOG.md for the full postmortem on each: 1. Pipeline health monitoring + alerting — a site whose feed silently goes stale is detectable (stale_sites()), not invisible until someone manually checks a report. 2. Orchestration state machine + safe resume — a mid-run failure never forces redoing already-completed, expensive work, and never leaves a half-written final output.

Run it yourself:

pip install -r ../../requirements.txt
pytest tests/ -v          # deterministic, no network required
python pipeline.py --live # hits the real Open-Meteo endpoint

What this is / isn't: a small demonstration pipeline built to make two specific, realistic production failure modes concrete and testable — not a claim that this is any specific employer's actual architecture.

Build Log — the postmortem

Build Log — Solar Pipeline

Postmortem-style log (Issue / Impact / Root Cause / Fix / Prevention) — see ../../EVALUATION_RUBRIC.md.

Issue #7 — No way to detect a site whose feed has gone silently stale

Found: while reasoning about a multi-site deployment (irradiance data pulled per-site, e.g. per install location) and asking "how would we actually know if one site's feed died — stopped updating, or started returning stale/cached data — without a human happening to notice a report looked wrong weeks later?"

Impact: the naive ingestion loop fetches every site and returns whatever it got, with zero record of when each site last succeeded. A site whose feed silently degrades (sensor failure, upstream API starts 200-ing with stale cached data instead of erroring) is indistinguishable from a healthy site in the pipeline's own output — there is nothing to alert on.

Root cause: "fetched successfully" was never recorded as a fact with a timestamp — only the fetched data was kept, and stale data looks structurally identical to fresh data.

Fix: HealthMonitor (pipeline.py) records a last-success timestamp per site on every successful fetch. stale_sites(now, threshold_seconds) returns exactly which sites have exceeded the freshness threshold — the actual input a real alerting hook (PagerDuty, Slack webhook, etc.) would consume, not just a passive log line.

Prevention: tests/test_health_monitoring.py — an xfail test proving the naive ingestion path has no staleness-detection surface at all, plus tests confirming the monitor correctly identifies a stale site past threshold and correctly reports a clean bill of health when nothing is stale.

Issue #8 — A mid-run failure forces redoing already-completed, expensive work

Found: while simulating a transient failure partway through a 4-step run (fetch → normalize → compute → write) and asking what a retry actually has to redo.

Impact: the naive run executes all four steps as one unit with no persisted checkpoint. If normalize fails after fetch already succeeded, nothing about that fact is recorded — a retry has no choice but to call fetch again from scratch, even though it already worked. For a real deployment where fetch is a network call against a rate-limited or slow upstream API, this isn't just wasteful — it makes recovery from a transient mid-run failure meaningfully slower and, at scale, can itself trigger the very rate limit that caused problems in the first place.

Root cause: the run's progress lived only on the call stack, not in any persisted state. When the call stack unwinds on an exception, the progress goes with it.

Fix: PipelineRun (pipeline.py) persists a state (PENDING → INGESTED → NORMALIZED → COMPUTED → WRITTEN) and the data produced by each completed step. advance_one_step() executes only the single next step for the run's current state; run_to_completion() loops it. A retry calls the same function again — it naturally resumes from the last successfully completed step, never re-running finished work and never producing a half-written final output (the write step only ever runs once state has reached COMPUTED).

Prevention: tests/test_orchestration_resume.py — an xfail test proving the naive run calls fetch twice across a fail-then-retry sequence, plus a test confirming the fixed version calls fetch exactly once and correctly resumes from INGESTED straight through to WRITTEN on the second call.

from typing import Callable


def ingest_all_naive(site_ids: list[str], fetch_fn: Callable[[str], dict]) -> dict[str, dict]:
    """Fetches each site and returns whatever it got — there is no record of *when*
    a site last succeeded, so a site that starts silently returning stale/empty data
    (a sensor feed dies, an upstream API starts 200-ing with no data) is
    indistinguishable from a healthy one until someone manually notices a report
    looks wrong.

    for site_id in site_ids:
        results[site_id] = fetch_fn(site_id)
    return results

def run_naive(
    site_id: str,
    fetch_fn: Callable[[str], dict],
    normalize_fn: Callable[[dict], dict],
    compute_fn: Callable[[dict], float],
    write_fn: Callable[[str, float], None],
) -> None:
    """Runs all four steps in one shot. If normalize_fn or compute_fn raises,
    nothing about *how far the run got* is recorded anywhere — a caller that
    retries has no choice but to call fetch_fn again from scratch, even though
    fetch (the expensive network step) already succeeded the first time.
    """

    normalized = normalize_fn(raw)
    kpi = compute_fn(normalized)
    write_fn(site_id, kpi)

After — pipelines/solar/pipeline.py (the fix, current on main)

"""
Solar pipeline — multi-site irradiance ingestion with health monitoring, and a
resumable multi-step orchestration run.

Same I/O/logic separation as the other pipelines. Live source: Open-Meteo's free
weather API (no key), the same real source already used elsewhere in this account's
public solar capability demo.

Two production issues are fixed here; see BUILD_LOG.md for the full postmortem on each:
  7. Pipeline health monitoring + alerting (HealthMonitor)
  8. Orchestration state machine + safe resume (PipelineRun, advance_one_step)
"""
from __future__ import annotations

import time
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable

import requests

OPEN_METEO_URL = "https://api.open-meteo.com/v1/forecast"


# ---------------------------------------------------------------------------
# Issue #7 — health monitoring + alerting
# ---------------------------------------------------------------------------

@dataclass
class HealthMonitor:
    """Fix for issue #7: tracks the last successful ingest time per site, so a site
    that silently stops producing fresh data is *detectable* instead of only
    noticed weeks later when someone happens to check a report.
    """

    _last_success: dict[str, float] = field(default_factory=dict)

    def record_success(self, site_id: str, ts: float | None = None) -> None:
        self._last_success[site_id] = ts if ts is not None else time.time()

    def last_success(self, site_id: str) -> float | None:
        return self._last_success.get(site_id)

    def stale_sites(self, now: float, threshold_seconds: float) -> list[str]:
        """Sites that have never succeeded, or whose last success is older than
        the threshold — the set that should trigger an alert.
        """
        stale = []
        for site_id, last_ts in self._last_success.items():
            if now - last_ts > threshold_seconds:
                stale.append(site_id)
        return stale


# ---------------------------------------------------------------------------
# Issue #8 — orchestration state machine + safe resume
# ---------------------------------------------------------------------------

class RunState(str, Enum):
    PENDING = "PENDING"
    INGESTED = "INGESTED"
    NORMALIZED = "NORMALIZED"
    COMPUTED = "COMPUTED"
    WRITTEN = "WRITTEN"


@dataclass
class PipelineRun:
    """Fix for issue #8: persists which step a run has actually completed, so a
    retry after a mid-run failure resumes from the last completed step instead of
    redoing already-finished (possibly expensive, e.g. network) work, and never
    produces a half-written final output.
    """

    site_id: str
    state: RunState = RunState.PENDING
    data: dict = field(default_factory=dict)


def advance_one_step(
    run: PipelineRun,
    fetch_fn: Callable[[str], dict],
    normalize_fn: Callable[[dict], dict],
    compute_fn: Callable[[dict], float],
    write_fn: Callable[[str, float], None],
) -> None:
    """Executes exactly the next step for `run`'s current state, and only advances
    `run.state` if that step succeeds. Raises without corrupting `run` if the step
    fails — the caller can inspect/retry `run` and this function will pick up
    exactly where it left off.
    """
    if run.state == RunState.PENDING:
        run.data["raw"] = fetch_fn(run.site_id)
        run.state = RunState.INGESTED
    elif run.state == RunState.INGESTED:
        run.data["normalized"] = normalize_fn(run.data["raw"])
        run.state = RunState.NORMALIZED
    elif run.state == RunState.NORMALIZED:
        run.data["kpi"] = compute_fn(run.data["normalized"])
        run.state = RunState.COMPUTED
    elif run.state == RunState.COMPUTED:
        write_fn(run.site_id, run.data["kpi"])
        run.state = RunState.WRITTEN
    # RunState.WRITTEN: nothing left to do — calling advance again is a safe no-op
    # at the call site (run_to_completion below stops the loop at WRITTEN).


def run_to_completion(
    run: PipelineRun,
    fetch_fn: Callable[[str], dict],
    normalize_fn: Callable[[dict], dict],
    compute_fn: Callable[[dict], float],
    write_fn: Callable[[str, float], None],
) -> None:
    while run.state != RunState.WRITTEN:
        advance_one_step(run, fetch_fn, normalize_fn, compute_fn, write_fn)


def fetch_live_irradiance(latitude: float, longitude: float) -> dict:
    resp = requests.get(
        OPEN_METEO_URL,
        params={
            "latitude": latitude,
            "longitude": longitude,
            "hourly": "shortwave_radiation",
            "forecast_days": 1,
        },
        timeout=10,
    )
    resp.raise_for_status()
    return resp.json()


if __name__ == "__main__":
    import sys

    if "--live" in sys.argv:
        monitor = HealthMonitor()
        sites = {"brooklyn_ny": (40.6782, -73.9442), "phoenix_az": (33.4484, -112.0740)}
        for site_id, (lat, lon) in sites.items():
            data = fetch_live_irradiance(lat, lon)
            values = data["hourly"]["shortwave_radiation"]
            peak = max(v for v in values if v is not None)
            monitor.record_success(site_id)
            print(f"{site_id}: peak shortwave radiation today = {peak} W/m^2")
        print("Stale sites (>1hr since success):", monitor.stale_sites(time.time(), 3600))
    else:
        print("Run with --live to hit the real Open-Meteo endpoint. "
              "See tests/ for deterministic unit tests of the monitoring/orchestration logic.")
